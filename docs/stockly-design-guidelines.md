# Stockly 디자인 지침

마지막 정리: 2026-08-20
상태: 작업 기준 초안

이 문서는 Stockly의 화면을 새로 만들거나 기존 화면을 개선할 때 사용하는 공통 디자인 기준이다. 목표는 토스의 시각 스타일을 그대로 복제하는 것이 아니라, 매장 직원이 짧은 시간 안에 다음 업무를 판단하고 처리할 수 있는 일관된 경험을 만드는 것이다.

이 문서는 구현 완료를 의미하지 않는다. 현재 화면과 차이가 있는 항목은 `docs/stockly-todo-list.md`의 UI 작업으로 분리해 순차적으로 적용한다.

## 1. 핵심 원칙

### 1.1 정보보다 다음 행동을 먼저 보여준다

Stockly는 정보를 열람하는 앱이 아니라 재고 업무를 처리하는 앱이다. 화면을 설계할 때 다음 질문에 먼저 답한다.

1. 사용자가 지금 해결하려는 업무는 무엇인가?
2. 이 화면의 가장 중요한 행동은 무엇인가?
3. 행동을 완료했는지 어떻게 알 수 있는가?
4. 잘못 처리했을 때 어떻게 되돌릴 수 있는가?

### 1.2 한 화면에는 주 행동을 하나만 둔다

- 주 행동은 한 가지 색상과 가장 높은 시각적 위계로 표시한다.
- 보조 행동은 텍스트 버튼, 아이콘 버튼, 상세 화면으로 내린다.
- 기능이 많다는 이유로 같은 크기의 카드와 버튼을 병렬로 늘어놓지 않는다.
- 여러 업무를 보여주더라도 사용자가 무엇부터 할지 순서가 보여야 한다.

### 1.3 조용하지만 상태는 분명하게 보여준다

- 기본 화면은 중립색과 충분한 여백을 사용한다.
- 빨강은 부족·긴급·오류처럼 즉시 확인해야 하는 상태에만 사용한다.
- 색상만으로 상태를 전달하지 않고 문구, 아이콘, 위치를 함께 사용한다.
- 장식적인 그래픽보다 상품명, 수량, 위치, 다음 행동의 가독성을 우선한다.

### 1.4 기본 상태와 예외 상태를 함께 설계한다

모든 주요 컴포넌트는 최소한 다음 상태를 정의한다.

- 기본
- 누름/선택
- 비활성
- 로딩
- 성공
- 오류
- 긴 문구
- 큰 글씨
- 다크모드
- reduced motion

### 1.5 완료 피드백과 복구를 기본으로 한다

저장·입고·발주·삭제 같은 행동은 결과가 즉시 보여야 한다.

- 처리 중: 중복 입력을 막고 현재 상태를 보여준다.
- 완료: 무엇이 바뀌었는지 짧게 알린다.
- 복구 가능: 확인창보다 `되돌리기`를 우선 검토한다.
- 실패: 오류 원문보다 사용자가 다음에 할 일을 보여준다.

## 2. Stockly의 업무 구조

화면 구조는 기능 목록이 아니라 직원의 업무 순서를 기준으로 구성한다.

```text
홈
 ├─ 오늘 가장 중요한 업무 확인
 ├─ 부족재고·입고예정·To do 확인
 └─ 스캔 또는 해당 업무로 이동

재고
 ├─ 상품 검색·필터
 ├─ 현재 수량·최소 수량·위치 확인
 └─ 상품 선택 → 재고 작업

스캔
 ├─ 바코드 인식
 ├─ 등록 상품이면 재고 작업으로 이동
 └─ 미등록 상품이면 상품 등록으로 이동

더보기
 ├─ 프랩·단체주문
 ├─ 기준정보·발주처
 ├─ 직원·권한
 └─ 환경설정·작업로그
```

## 3. 내비게이션 지침

### 3.1 모바일 기본 구조

기본안은 다음 네 가지 하단 메뉴를 사용한다.

| 메뉴 | 역할 | 주요 진입점 |
| --- | --- | --- |
| 홈 | 오늘 처리할 업무 요약 | 부족재고, 입고, To do, 인수인계 |
| 재고 | 상품과 수량 탐색 | 검색, 카테고리, 상품 상세 |
| 스캔 | 가장 빠른 상품 진입 | 바코드, 이미지 스캔 |
| 더보기 | 자주 쓰지 않는 기능과 관리 | 프랩, 단체주문, 설정, 작업로그 |

현재 `부족재고`와 `작업로그`가 하단 메뉴에 있는 경우에는 실제 사용 빈도와 접근 경로를 확인한 뒤 단계적으로 조정한다. route, history, 권한, 스캔 복귀 동작을 먼저 보존한다.

### 3.2 부족재고 접근

부족재고는 중요한 업무이지만 항상 별도의 5번째 메뉴일 필요는 없다.

- 홈의 요약 수치와 우선 업무 카드에서 진입한다.
- 재고 목록에서는 부족 상태 필터와 배지로 진입한다.
- 스캔 결과가 부족 상태라면 바로 발주 또는 재고 작업으로 이어진다.
- 하단 메뉴에서 숨기는 경우에도 한 번의 추가 탐색으로 찾을 수 있어야 한다.

### 3.3 관리 메뉴

상단 메뉴 또는 더보기 화면은 기능을 나열하지 않고 업무 영역별로 그룹화한다.

- 재고 운영: 작업로그, 부족재고 관련 도구
- 프랩·단체주문: 프랩관리모드, 단체주문 계산, 레시피
- 기준정보: 카테고리, 품목 단위, 발주처
- 직원·설정: 직원 관리, 권한, 환경설정

현재 권한으로 사용할 수 없는 그룹은 숨긴다. 권한이 없어 접근할 수 없는 메뉴를 보여준 뒤 오류로 막는 방식은 사용하지 않는다.

## 4. 홈 화면 지침: 오늘의 업무 우선순위

### 4.1 홈의 목적

홈은 모든 데이터를 보여주는 대시보드가 아니라, 직원이 앱을 연 뒤 3초 안에 “무엇부터 할지” 결정하는 화면이다.

### 4.2 권장 화면 순서

```text
상단 헤더
  Stockly · 권한 · 메뉴

오늘의 업무
  날짜 · 오늘/내일 전환

오늘 가장 중요한 업무
  부족재고 3건을 먼저 확인해 주세요
  긴급 1건 · 입고예정 2건 · 미완료 To do 1건
  [스캔으로 바로 확인]

요약
  부족재고 3 · 입고예정 2 · 미완료 To do 1

지금 할 일
  부족재고 확인
  입고예정 확인
  오픈 전 To do

다음 단계
  발주 목록 정리 또는 인수인계 작성

하단 내비게이션
```

### 4.3 우선순위 계산

실제 우선순위는 매장 업무 정책에 따라 조정할 수 있지만, 기본 순서는 다음을 사용한다.

1. 긴급·부족재고
2. 오늘 입고 예정 또는 입고 확인
3. 근무 시간에 맞춰야 하는 To do
4. 인수인계
5. 과거 기록·통계·설정

수치가 0인 영역은 무조건 큰 카드로 남기지 않는다. 빈 상태 문구와 다음 행동만 간결하게 보여준다.

### 4.4 오늘/내일 전환

- 오늘 화면은 지금 처리해야 하는 업무를 우선한다.
- 내일 화면은 다음 근무자 준비, 입고 예정, 인수인계를 우선한다.
- 날짜 선택 UI가 업무 목적보다 먼저 눈에 띄지 않게 한다.
- 오늘과 내일의 데이터가 섞이지 않도록 제목과 설명을 명확히 구분한다.

## 5. 주요 화면 패턴

### 5.1 재고 목록

상품 한 행 또는 카드에는 다음 정보를 우선순위 순서대로 표시한다.

1. 상품명
2. 현재 총재고
3. 최소재고 또는 상태
4. 창고·매장 위치
5. 부족·긴급·중요 품목 상태
6. 다음 행동

상품명과 수량이 가장 먼저 읽혀야 하며, 발주처·단위·최근 활동과 같은 보조 정보는 한 단계 낮은 위계로 표시한다.

### 5.2 재고 작업

재고 작업 화면은 입력 과정에서 판단해야 할 내용을 줄인다.

- 상품명과 현재 총재고를 상단에 고정한다.
- `입고 / 출고 / 이동 / 조정`을 명확한 선택 그룹으로 제공한다.
- 수량 입력은 큰 숫자와 빠른 수량 버튼을 사용한다.
- 위치가 필요한 작업은 `창고 / 매장`을 먼저 선택한다.
- 저장 버튼은 화면 하단에서 쉽게 닿고, 저장 중에는 중복 입력을 막는다.
- 저장 완료 후 변경 수량과 마지막 저장 시각을 보여준다.

### 5.3 스캔

스캔은 상품을 찾는 중간 화면이 아니라 업무를 시작하는 진입점이다.

- 카메라 화면에서는 스캔 가능 영역과 현재 상태를 명확히 보여준다.
- 등록 상품: 상품명·현재 수량·다음 행동을 즉시 보여준다.
- 미등록 바코드: “등록되지 않은 바코드입니다”와 `상품 등록`을 제공한다.
- 중복·인식 실패·카메라 권한 오류는 서로 다른 문구와 해결 방법을 사용한다.
- 스캔 결과를 확인한 뒤 재고 작업으로 이동할 때 이전 화면과 스캔 상태를 잃지 않는다.

### 5.4 부족재고와 발주

부족재고 화면은 원인과 다음 행동이 연결되어야 한다.

| 상태 | 표시 | 다음 행동 |
| --- | --- | --- |
| 최소재고 이하 | 부족 | 재고 작업 또는 발주 수량 입력 |
| 상태 기반 발주 필요 | 발주 필요 | 상태 확인 또는 발주 |
| 수동 추가 | 추가 | 필요 수량 입력 |
| 긴급 | 긴급 | 우선 발주 또는 담당자 확인 |
| 입고 확인 전용 | 입고 확인 | 실제 수량 대신 입고 여부 처리 |

`부족 → 발주 목록 추가 → 발주처별 발주 → 입고 확인`의 흐름을 끊지 않는다.

## 6. 디자인 토큰

값을 직접 복사해 쓰기보다 의미 기반 토큰을 사용한다. 실제 값은 구현 과정에서 현재 Stockly 브랜드와 접근성 대비를 확인하며 확정한다.

### 6.1 색상 의미

| 의미 토큰 | 용도 | 기본 방향 |
| --- | --- | --- |
| `brand` | 주 행동, 선택, 링크 | Stockly 보라색 계열 |
| `neutral` | 기본 텍스트, 배경, 구분선 | 차분한 회색 계열 |
| `danger` | 부족, 긴급, 삭제, 오류 | 빨강 계열 |
| `warning` | 입고 예정, 주의 | 주황·황색 계열 |
| `success` | 저장 완료, 입고 완료 | 초록 계열 |
| `info` | 안내, 보조 정보 | 브랜드 또는 중립 계열 |

색상은 상태의 유일한 표현 수단이 아니다. 항상 라벨이나 아이콘을 함께 사용한다.

### 6.2 간격과 모서리

- 기본 간격: 4, 8, 12, 16, 24, 32
- 화면 좌우 여백: 모바일 16px을 기본으로 하되 좁은 화면에서 12px까지 조정
- 작은 컨트롤 모서리: 8px
- 카드·목록 그룹 모서리: 12~16px
- 강조 영역 모서리: 16~20px
- 카드 안에 카드를 중첩하지 않는다.

### 6.3 타이포그래피

- 화면 제목: 한 문장으로 짧게, 굵은 위계
- 섹션 제목: 무엇을 확인하는 영역인지 명확하게
- 주요 수량: `tabular-nums`와 충분한 크기
- 보조 설명: 짧고 한두 줄 이내
- 필수 정보는 11px보다 작게 만들지 않는다.
- 상품명이 길어져도 잘리지 않고 줄바꿈 또는 말줄임 정책이 일관되게 작동해야 한다.

### 6.4 터치 영역

- 터치 가능한 버튼은 시각 크기와 관계없이 44×44px 이상을 확보한다.
- 아이콘만 있는 버튼은 `aria-label`과 툴팁 또는 주변 문맥을 제공한다.
- 인접한 삭제·저장·이동 버튼은 오작동하지 않도록 간격을 둔다.

## 7. 공통 컴포넌트 지침

### Button

- `primary`: 화면의 주 행동 하나
- `secondary`: 주 행동을 보조하거나 취소
- `quiet`: 목록 안의 가벼운 이동·편집
- `destructive`: 삭제·취소처럼 손실 위험이 있는 행동

버튼 문구는 기능명보다 결과를 우선한다.

- 좋은 예: `재고 저장`, `발주 목록에 추가`, `스캔 시작`
- 피할 예: `확인`, `처리`, `실행`처럼 결과가 모호한 문구

### Status

상태 배지는 짧은 단어 하나를 기본으로 하고, 같은 상태는 모든 화면에서 같은 색·아이콘·문구를 사용한다.

- `부족`: 최소재고 기준 미달
- `발주 필요`: 상태 기능에서 발주가 필요한 상태
- `긴급`: 우선 처리가 필요한 수동 표시
- `입고예정`: 아직 실제 입고되지 않음
- `입고완료`: 입고 기록이 남음
- `확인 필요`: 사용자가 판단해야 함

### ListRow

목록 행은 `핵심 정보 → 보조 정보 → 상태 → 다음 행동` 순서로 읽힌다. 삭제·편집 아이콘이 상품명보다 먼저 눈에 띄지 않게 한다.

### Modal / Bottom Sheet

- 단순 선택은 메뉴 또는 바텀시트로 처리한다.
- 입력·확인·히스토리처럼 집중이 필요한 작업은 모달로 처리한다.
- 모달 제목은 한 문장으로 명확히 한다.
- ESC, 배경 닫기 정책, 닫기 버튼, 첫 포커스, 닫은 뒤 포커스 복귀를 정의한다.
- 데이터 손실 가능성이 있는 경우 destructive 버튼을 명확히 구분한다.

### EmptyState

빈 상태는 “없음”으로 끝내지 않고 다음 행동을 제시한다.

- 부족재고 없음: `현재 부족재고가 없습니다.`
- 상품 없음: `등록된 품목이 없습니다. 상품을 추가해 보세요.`
- 검색 결과 없음: `검색 결과가 없습니다. 상품명이나 바코드를 확인해 주세요.`

## 8. 상태·오류·복구 지침

### 로딩

- 화면 첫 로딩은 구조를 예상할 수 있는 skeleton을 사용한다.
- 짧은 작업은 버튼을 `저장 중...`처럼 변경하고 중복 입력을 막는다.
- 로딩이 길어지면 무엇을 불러오는지 설명한다.

### 오류

오류 문구는 원인과 다음 행동을 포함한다.

```text
무엇이 문제인가요?
왜 발생했나요?
지금 무엇을 하면 되나요?
```

예시:

- 나쁜 예: `duplicate key value violates unique constraint`
- 좋은 예: `같은 바코드가 이미 다른 품목에 등록되어 있습니다. 기존 품목을 확인해 주세요.`

### 저장과 되돌리기

- 저장 중에는 같은 요청을 반복해서 보내지 않는다.
- 성공 메시지는 바뀐 대상을 포함한다.
- 되돌리기가 가능하면 성공 메시지에 바로 노출한다.
- 되돌릴 수 없는 삭제·탈퇴는 공통 확인 모달을 사용한다.

## 9. 인터랙션과 모션

Stockly의 모션은 장식이 아니라 상태 변화와 공간 관계를 설명하는 데 사용한다. ERP 성격의 업무 앱이므로 시각적 화려함보다 입력 반응, 목록 스크롤, 수량 정확성, 스캔 안정성을 우선한다.

기본 방향은 **가만히 있을 때는 조용하고, 조작했을 때만 빠르게 반응하는 UI**다. 한 화면에서 사용자가 주목해야 하는 주연 모션은 하나만 두고, 나머지는 짧은 조작 피드백으로 제한한다.

### 9.1 성능을 판단하는 기준

애니메이션의 개수만으로 성능을 판단하지 않는다. 다음 항목을 함께 확인한다.

1. 어떤 CSS 속성을 움직이는가?
2. 몇 개의 요소가 동시에 움직이는가?
3. 얼마나 큰 화면 영역을 다시 그리는가?
4. 얼마나 오래 또는 반복해서 실행되는가?
5. 프레임마다 JavaScript 계산이나 React 렌더링이 발생하는가?
6. 스크롤·드래그·카메라·키보드 입력과 동시에 실행되는가?

짧은 `transform`·`opacity` 전환 여러 개보다 화면 전체의 블러, 레이아웃 변경 또는 무한 반복 효과 하나가 더 큰 비용을 만들 수 있다.

### 9.2 예쁜 UI를 만드는 우선순위

애니메이션을 늘리기 전에 다음 순서로 정적인 완성도를 높인다.

1. 정보 위계와 여백
2. 타이포그래피와 숫자 정렬
3. 버튼·필드·카드·배지 규칙의 일관성
4. 선택·긴급·오류·완료 색상의 명확한 구분
5. 모바일과 데스크톱에 맞는 정보 밀도
6. 상태 변화를 설명하는 짧은 모션

애니메이션을 제거했을 때도 상품명, 수량, 현재 상태, 다음 행동을 이해할 수 있어야 한다. 모션은 좋은 구조를 보완하며 불명확한 정보 구조를 대신하지 않는다.

### 9.3 상황별 모션 사용 기준

| 상황 | 피드백 |
| --- | --- |
| 버튼 누름 | 짧은 눌림 피드백 |
| 스캔 성공 | 성공 상태와 다음 행동을 즉시 표시 |
| 저장 중 | 진행 상태와 중복 방지 |
| 저장 완료 | 성공 메시지와 마지막 저장 시각 |
| 삭제 완료 | 삭제 결과와 되돌리기 |
| 화면 전환 | 상위 화면과 하위 화면의 관계가 느껴지는 전환 |

다음 세 단계로 적용 여부를 결정한다.

| 구분 | 패턴 | 기준 |
| --- | --- | --- |
| 권장 | 버튼 눌림, 탭 indicator, 상태 메시지, 작은 메뉴 펼침, 모달·바텀시트 | 짧고 국소적이며 사용자의 행동 결과를 설명한다. |
| 조건부 | 화면 진입, 짧은 목록 stagger, skeleton shimmer, 작은 영역의 높이 변화, sticky 영역의 blur | 범위와 동시 실행 수를 제한하고 실제 기기에서 확인한다. |
| 회피 | 대량 목록 전체 등장, 무한 그라데이션·광택·펄스, 스크롤 패럴랙스, 큰 영역 blur·shadow 애니메이션, 수량 animated counter | 업무 입력과 스크롤을 방해하거나 정확한 값의 인지를 늦출 수 있다. |

### 9.4 모션 성능 예산

- 기존 `motion`과 `src/lib/animations.ts`를 공통 기준으로 사용한다. 일반적인 UI 모션을 위해 별도 애니메이션 라이브러리를 추가하지 않는다.
- 기본 지속 시간은 `fast 160ms`, `normal 200ms`, `slow 250ms` 범위로 유지한다.
- 일반 전환은 `transform`과 `opacity`를 우선한다.
- `width`, `height`, `top`, `left`, `margin`, `padding`, 복잡한 grid 변경처럼 매 프레임 레이아웃을 다시 계산하는 전환은 작은 국소 영역에서만 예외적으로 사용한다.
- 업무 화면의 무한 반복 애니메이션은 실제 진행 중인 로딩 표시 외에는 사용하지 않는다.
- 목록 stagger는 대략 10개 이하의 짧은 목록에서만 검토한다. 재고처럼 항목 수가 많거나 필터·재조회가 잦은 목록에는 적용하지 않는다.
- 데이터 갱신 때마다 같은 항목이 다시 등장하는 애니메이션을 실행하지 않는다.
- skeleton은 실제 화면 구조를 대표하는 제한된 개수만 보여주고, 로딩이 끝나면 즉시 제거한다.
- `will-change`는 공통 클래스에 상시 부여하지 않는다. 필요하면 애니메이션 직전에 적용하고 종료 후 제거한다.
- `backdrop-blur`, `filter`, 큰 그림자는 스크롤 영역과 sticky header에서 제한적으로 사용하고, 성능 문제가 있으면 불투명 배경으로 대체한다.
- 저장·입고·출고·조정 결과는 애니메이션 완료를 기다리지 않고 즉시 반영한다. 수량 자체를 천천히 변화시키지 말고, 필요하면 주변 강조만 짧게 사용한다.

### 9.5 Stockly 구현 규칙

- route 전환은 짧은 진입 효과를 기본으로 하고, 뒤로가기와 스크롤 복원을 방해할 수 있는 exit 애니메이션은 사용하지 않는다.
- 모달과 바텀시트는 overlay의 `opacity`와 panel의 `transform`을 사용한다. 포커스 이동, 버튼 활성화, 배경 입력 차단은 애니메이션과 관계없이 즉시 적용한다.
- 바코드 스캔, 수량 휠 드래그, 긴 목록 스크롤 중에는 장식 모션이 입력 처리와 경쟁하지 않게 한다.
- 지속적으로 프레임을 갱신하는 그라데이션과 장식 효과는 공개 랜딩·온보딩처럼 업무 외 화면으로 제한한다.
- `prefers-reduced-motion`에서는 이동·확대·stagger·shimmer를 제거하거나 거의 즉시 끝낸다. 색상, 문구, 아이콘처럼 결과를 설명하는 피드백은 유지한다.
- 모션만으로 성공·실패·선택 상태를 전달하지 않는다.

현재 파일별 적용 현황과 별도 점검 항목은 [Stockly 애니메이션 적용 현황](./animation-implementation.md)에서 관리한다.

### 9.6 검증 기준

정적 코드 확인, build, lint만으로 애니메이션 성능과 체감 품질이 검증됐다고 판단하지 않는다. 한 종류의 모션을 대표 화면에 먼저 적용하고 다음 조건을 확인한 뒤 같은 패턴을 확장한다.

- 실제 지원 대상 중 성능이 낮은 iPhone·Android 기기와 WebView
- 한국어 장문 상품명과 200개 이상의 재고 항목
- 재고 목록 스크롤과 검색·필터 변경
- 수량 휠 드래그와 키패드 입력
- 바코드 카메라 실행과 스캔 결과 이동
- 모달·바텀시트 연속 열기와 닫기
- 저장 직후 수량·상태 메시지·작업 로그 반영
- skeleton에서 실제 콘텐츠로 바뀔 때의 높이 변화
- 다크모드와 `prefers-reduced-motion`

검증할 때는 변경 전후의 브라우저 Performance 기록과 실제 기기 체감을 비교한다. 프레임 저하, 긴 메인 스레드 작업, 터치 응답 지연, 발열·배터리 증가가 보이면 장식 모션부터 줄인다.

## 10. 문구와 콘텐츠

### 10.1 결과 중심 문구

사용자가 얻는 결과가 먼저 보이도록 작성한다.

| 상황 | 권장 | 피할 표현 |
| --- | --- | --- |
| 스캔 진입 | 스캔 시작 | 스캔 실행 |
| 부족재고 | 부족재고 3건 확인 | 부족재고 데이터 조회 |
| 저장 | 재고 저장 | 확인 |
| 발주 | 발주 목록에 추가 | 선택 |
| 완료 | 입고 완료 처리 | 처리 완료 |
| 오류 | 다시 시도하거나 상품 정보를 확인해 주세요 | 오류가 발생했습니다 |

### 10.2 표기 통일

문서와 화면에서 다음 표기를 통일한다.

- `To do` 또는 `할 일` 중 하나를 제품 전체에서 선택
- `재고현황`과 `재고 현황` 중 하나를 선택
- `부족재고`와 `부족 재고` 중 하나를 선택
- `컨펌`은 내부 운영 용어로 사용할 때 설명을 함께 제공
- `입고예정`, `입고완료`는 상태 라벨로 고정

## 11. 접근성과 반응형

### 접근성 체크

- 활성 하단 메뉴에 `aria-current="page"`와 색상 외 표시를 함께 제공한다.
- 성공은 `role="status"`, 즉시 조치가 필요한 오류는 `role="alert"`를 사용한다.
- 모달은 `role="dialog"`, `aria-modal="true"`, 제목 연결, 첫 포커스, ESC, 포커스 복귀를 지원한다.
- 아이콘 버튼은 모양이 아니라 기능을 읽어준다.
- 체크박스·수량·상태는 색상 없이도 이해할 수 있어야 한다.
- 큰 글씨 환경에서 고정 높이와 한 줄 버튼 문구가 깨지지 않아야 한다.

### 반응형 체크

최소 다음 환경을 확인한다.

- 320×568 모바일
- 일반 모바일
- 태블릿 또는 넓은 데스크톱
- 큰 글씨 환경
- 키보드가 열린 상태
- 다크모드
- `prefers-reduced-motion`

모바일 화면을 데스크톱의 축소판으로 만들지 않는다. 좁은 화면에서는 정보량과 탐색 방식을 줄이고, 넓은 화면에서는 콘텐츠 폭과 내비게이션을 확장한다.

## 12. 화면 설계 작업 순서

모든 화면을 한 번에 다시 만들지 않는다.

### 1단계: 정보 구조

- `UI-012`: 홈을 오늘의 업무 우선순위 화면으로 재설계
- `UI-013`: 메인 내비게이션과 더보기 구조 정리
- 화면별 주 사용자, 주 행동, 완료 상태를 한 줄로 기록

### 2단계: 공통 규칙

- `UI-014`: 색상·간격·타이포그래피·컴포넌트 변형 정의
- `UI-017`: 문구와 상태 라벨 통일
- 반복되는 페이지별 스타일을 목록화

### 3단계: 상태와 인터랙션

- `UI-015`: 로딩·빈 상태·오류·성공·되돌리기 통합
- `UI-016`: 저장·스캔·발주·삭제 모션과 피드백 정의
- 데이터가 바뀌는 흐름부터 실제 화면에 적용

### 4단계: 적용과 검증

- 홈 → 부족재고 → 재고 작업 → 스캔 순서로 적용
- `UI-003`~`UI-011`, `UI-018`의 접근성·반응형 조건 확인
- 모바일과 데스크톱 화면을 전후 비교
- 기능·권한·route·DB 의미가 바뀌지 않았는지 확인

## 13. 리뷰 체크리스트

화면을 완료 처리하기 전에 다음 질문에 모두 답한다.

- 이 화면의 주 사용자는 누구인가?
- 사용자가 지금 하려는 업무가 첫 화면에서 보이는가?
- 주 행동이 하나로 구분되는가?
- 상품명·수량·상태·다음 행동이 올바른 순서로 읽히는가?
- 로딩·빈 상태·오류·성공 상태가 정의되어 있는가?
- 잘못 처리했을 때 되돌릴 수 있는가?
- 긴 문구와 큰 글씨에서 깨지지 않는가?
- 색상 없이도 상태를 이해할 수 있는가?
- 키보드·VoiceOver·터치로 사용할 수 있는가?
- 모바일과 넓은 화면에서 정보량이 적절한가?
